# 训练全流程与多机协同（面试用总结）

这是一个从零做起的项目：“分层图元画家”。模型不直接生成像素，而是按图层顺序，一笔一笔输出广义高斯笔触的参数。
本文按数据从产生到部署的顺序，把每一步做了什么、为什么这样做、实测结果和踩过的坑记下来。
所有数字都来自仓库里能复现的实验，出处见各节引用的文档。

```
原图 + 分层 mask ──分解器（可微渲染拟合）──▶ 笔触序列（每张图多条轨迹）
     │                                          │ 清理（删掉看不见的笔触）、校验（SHA、协议哈希、划分）
     ▼                                          ▼
  中文描述（VLM + 模板）              监督训练（两级 Transformer + 画布反馈 + 文字/图像条件）
                                                │
                                                ▼
                         GRPO 后训练（渲染出图后打分：CLIP + 属性 + 孤儿率）
                                                │
                                                ▼
            评估（独立评委 CLIP、属性分类器、留出属性、有无 CFG 分开看）
                                                │
                                                ▼
          ONNX 导出 ─▶ C++ 运行时（ORT CPU/CUDA，KV cache 常驻显存）─▶ 量化 / TensorRT（进行中）
```

## 1. 数据：从图片到笔触序列

### 1.1 原始数据和图层

- 人脸用 CelebAMask-HQ：3 万张，19 类人工分割标注，映射成 6 个图层：背景、身体、皮肤、五官、头发、配饰。
- 动漫用 anime_face_control_60k，筛选后 53,125 张。没有人工 mask，六层是伪标签：
  角色/背景用 anime-seg 分；五官、皮肤用 28 个关键点切出来；头发用“眉毛以上的颜色聚类 + 连通性”判断。
  被标记、需要人工复核的约 1%。
- 通用题材用 COCO Panoptic：每张图最多 8 个“槽位”（3 个背景组 + 1 个零碎物体槽 + 最大的 4 个物体实例），
  物体按包围框下沿从远到近排序（`docs/protocol_v3_design.md`）。

### 1.2 分解器：每张图怎么变成笔触序列

- 图元是广义高斯：位置、两个尺度、旋转角、边缘硬度 β、颜色、透明度，在 sRGB 空间做 premultiplied over 合成。
- 合成运算满足结合律：整张图一起渲染、按层渲染再叠加、分块渲染，结果完全相同。
  正因为这样，才能按层分解，后面也才能做按层重画（REDRAW）。
- 按层用可微渲染拟合：每层分若干轮，每轮在误差大的地方初始化新图元，用 Adam 优化 80 步；
  最后 30% 的步数做量化感知（直通估计）。
- 光栅化 kernel 我自己写了三个后端：Triton、CUDA，以及通过 hipify 移植到海光 DCU 的版本。
  分解器从稠密的参考实现每张 19.8 秒，降到 Triton 版每张 0.8 秒（`bench/REPORT_raster.md`）。

### 1.3 协议和量化

- v1 用的形状码本会损失 6.6 dB。v2 改成按属性分开分档（x/y 各 512 档、σ 128 档、θ 128 档、β 8 档），
  颜色用 k-means 码本。训练目标的画质从 24.9 dB 提高到 30.2 dB，连续参数的上限是 32.4 dB（`docs/protocol_v2.md`）。
- 协议文件和码本都算 SHA，记录在每个数据目录的 `config.json` 里。训练和推理开始前都会核对，避免混用不同版本的 token。

### 1.4 每张图多条轨迹（效果最大的一项）

- 同一张图换随机种子、或者水平翻转后重新分解，得到的笔触集合不一样。
  只给一条轨迹，模型会把这一次的随机结果当成标准答案去记。
- **实测：从 1 条增加到 4 条，评委 R@5 从 18.8% 升到 30.2%，属性一致率 +3.6 个点。**
  训练损失和验证损失的差距从 0.10 缩小到 0.02，过拟合的迹象消失了。
- POP 2 的作者用的是 5 万张图 × 150 条轨迹。我们现在在做 12 条，并用实测的收益曲线决定要不要继续往上加。

### 1.5 清理和校验

- 清理：删掉“几乎看不见”的图元（遮挡之后的可见量小于 2 个像素）。删掉了约 4% 的图元，平均 PSNR 只降 0.03 dB；
  如果删除导致某张图下降超过 0.1 dB，就保留原样。
- 划分：同一张原图的所有轨迹和翻转版本，必须落在同一个划分里（固定的 `split_manifest`），防止验证集泄漏。
- 跨机器校验：每个分片都算 SHA。合并之前核对每条轨迹是否覆盖全部 3 万张、图片 ID 是否一致、翻转和种子是否对得上。

### 1.6 文字描述

- 中文描述由 Qwen2.5-VL 自动生成，每张一长一短；另外有 CelebA 属性模板，每次随机组合；还有 10% 不给文字，供 CFG 使用。
- 水平翻转的轨迹会自动交换描述里的“左/右”。

## 2. 多机协同：三台异构机器怎么分工

| 机器 | 硬件 | 主要做什么 |
|---|---|---|
| 本机 | RTX 5070 笔记本 8GB | 开发和测试、分解偶数分片、动漫数据、C++ 运行时 |
| SCNet | 海光 DCU（BW，64GB，DTK/HIP） | 主训练，分解奇数分片 |
| 租用 | RTX 4090 24GB | 分解（数据工厂） |

**数据并行的分解：** 分片号按奇偶分给不同机器（`--part 0/2` 和 `1/2`），每台机器内部再按轨迹并行。
每个分片写完后做原子重命名，算 SHA，再汇总合并。

**环境不同，怎么保证结果一致：**
- 同一份 CUDA C++ 源码：在 NVIDIA 上用 nvcc 编译，在 DCU 上由 PyTorch 自动 hipify 后用 hipcc 编译。
  warp 是 32 线程还是 wavefront 是 64 线程，这类假设都去掉了；两边各跑同一套测试。
- 在租来的机器上用同一个脚本重新生成数据分片，**全部 61 个文件的 SHA 都和本机一致**，才开始分解。

**网络和链路的工程问题（都实测过）：**
- 家里上传到远程只有约 0.6–0.9 MB/s。所以传序列分片之前先用 zstd 压缩（缩到 56%）；
  只用来算特征的图片用 JPEG q95 打包（只有原来的 1/6，与原图相差 42.7 dB）；
  需要大量数据时，让远程机器从国内源（ModelScope）直接下载，再核对 SHA 是否和本地一致。
- 租来的机器访问海外要经过集群代理，很慢；改用国内的 PyPI 镜像和 ModelScope，下载时去掉代理。
- 进程管理：在远程用 `pkill -f` 时，模式会匹配到执行它的那个 shell 自己，结果把自己杀了。
  之后规定：一律按 PID 杀进程，复杂的操作先写成脚本文件上传再执行。
- 监控：写了一个跨三台机器的事件监控，汇报每条轨迹完成、训练里程碑和报错，失败时也一定会报出来。

### 多卡数据并行训练（DDP）：代码已写好，正确性已验证，扩展效率还没测

`tools/train.py` 支持 `torchrun` 启动（`torchrun --nproc_per_node=N tools/train.py ...`），单进程启动时行为和原来完全一样。

**实现要点：**
- 每张卡一个进程，用 `DistributedDataParallel` 在反向传播时对梯度做 all-reduce
  （NVIDIA 上用 NCCL；DTK/ROCm 上 RCCL 也叫 `nccl` 这个名字）。
- 数据用 `DistributedSampler`：每个 epoch，各个进程读互不重叠的一份，合起来正好覆盖整个 epoch；
  每个 epoch 调用 `set_epoch` 重新打乱，所有进程用同一个种子。有测试覆盖（`tests/test_ddp_loader.py`）。
- 数据扰动（历史扰动、去掉文字、REDRAW/REFINE 采样）的随机种子按进程号错开，避免几张卡做同样的扰动。
- 梯度累积：只在最后一个 micro-step 同步，前面的用 `no_sync()` 跳过 all-reduce，通信量除以累积步数。
- 只有 rank 0 做评估、出样张、写日志和保存 checkpoint；其他进程在下一次 all-reduce 处等它。
  吞吐日志里的 records/s 先 all-reduce 求和，记的是整个任务的吞吐。
- 结束时校验各个副本是否一致：每个参数算一个校验和，与 rank 0 广播过来的值比较。

**踩到的坑：** 第一次跑就卡在 “Expected to have finished reduction in the prior iteration”。
查出来是两类**永远拿不到梯度**的参数：
1. 最后一个属性（alpha）的嵌入投影：解码器里它后面没有别的属性了，所以这个嵌入不会被用到。
   单卡训练时它也一直没更新，只是没人发现。
2. 不带文字训练时的 `text_proj`。

DDP 会一直等这些参数的梯度。修法是在包装 DDP 之前把它们设为 `requires_grad=False`；
没有用 `find_unused_parameters=True`，因为那样每一步都要遍历一遍 autograd 图。
只有图像条件、目标图条件这类按 batch 时有时无的模块，才打开 `find_unused_parameters`。

**已经验证的（本机单卡，2 个进程共用一张卡，gloo 后端，tiny 模型，60 步）：**

| 配置 | 全局 batch | step 50 的 event / x 损失 | 结束时各副本参数差异 |
|---|---:|---|---|
| 单进程，batch 16 | 16 | 1.3026 / 6.168 | — |
| 2 个进程，每卡 batch 8 | 16 | 1.3035 / 6.173 | 0 |
| 2 个进程，每卡 batch 4 × 累积 2 | 16 | 1.3035 / 6.173 | 0 |

在全局 batch 相同的情况下，多进程的损失和单进程一致（剩下的差别来自数据顺序不同）；
加上梯度累积之后的结果和不累积时完全相同，说明 `no_sync` 的逻辑是对的。

**还没测的：** 真正多卡（NCCL）下的扩展效率、通信占比、显存。这需要租多卡机器，等用户决定。
测的时候计划记录：1/2/4/8 卡的吞吐和扩展效率，nsys 里 all-reduce 和反向传播的重叠情况，
以及 bucket 大小（`bucket_cap_mb`）对吞吐的影响。

**放大到 1B 时：** DDP 每张卡要放一份完整的参数、梯度和 AdamW 状态，1B 参数大约要 16 GB，再加上激活值，
24 GB 的卡就不够了。到时候换 FSDP（相当于 ZeRO-3：参数、梯度、优化器状态都切分到各卡），并开激活重计算。

## 3. 训练

### 3.1 模型

- 两级 Transformer。主干每个图元占一个位置；一个小解码器在每个位置上依次输出 1 个事件和 8 个属性
  （因果结构，所以一次完整前向就能同时监督全部属性）。
- 文字条件：冻结的 Chinese-CLIP 文字塔，特征池化成 32 个 token，作为前缀；训练时以 10% 概率去掉文字，推理时用 CFG。
- 画布反馈：每 32 个图元，以及每个控制记录处，把当前画布渲染成 64px，用一个小 CNN 编码，
  主干第 3、7 层用门控交叉注意力去读。训练和推理看到的画布逐像素一致，有测试保证。
- 历史扰动：30% 的序列会随机扰动一部分前缀，被扰动的记录不作为监督目标，让模型学会从错误里接着画。
- 图像条件：第一版用 CLIP 图像 token 作前缀；第二版读像素，用 ControlNet 式的零初始化输出投影。
  这个设计是踩了两次坑才定下来的：门初始化为 0 会卡住，初始化为 0.46 又会被优化器关掉（`docs/image_cond_log.md`）。

### 3.2 训练效率优化（`docs/perf_log.md`）

| 改动 | 效果 |
|---|---|
| DataLoader worker 从 2 增加到 4（定位到瓶颈是 CPU 上的样本组装） | 26k → 44k records/s，1.7 倍 |
| 把画布检查点的逐位置 Python 循环改成向量化（cumsum + cummax） | 37 ms → 0.07 ms/batch，约 540 倍 |
| 冻结的文字编码器结果做缓存（bf16，LRU） | 每步省掉约 1 亿参数模型的一次前向 |
| 采样器每条 record 只同步一次设备，语法 mask 在 CPU 上建好后一次拷贝 | 2 倍，输出逐 token 一致 |

### 3.3 训练配方和规模

- small（20M）：先在 1 条轨迹上训 8000 步，再在 4 条轨迹上训 12000 步。
- base（126M）：同步数下验证损失低约 0.18，而且差距在拉大，所以下一阶段用 base。
- 判断瓶颈在哪：训练损失约等于验证损失，说明没有过拟合，瓶颈在容量；
  一旦要放大到 1B，数据量会成为瓶颈，所以要同时扩充数据。

## 4. 后训练：GRPO（`docs/rl_log.md`）

- Rollout：每步 8 条提示词，每条采 8 个样本。采样时温度 1、不截断、不用 CFG，
  这样语法 mask 重放之后算出的 record 对数概率就是真实的采样概率。
- 奖励：CLIP 图文相似度；生成图是否带有描述来源那张图的属性（属性分类器的概率）；孤儿率。
- **关键教训：**
  1. 只用 CLIP 当奖励，会在奖励模型上作弊：换一个独立的评委 CLIP 来看，只有一半的提升是真的。
  2. 几个奖励直接相加时，CLIP 的方差是属性项的 8 倍左右，属性信号完全被淹没。
     改成每一项先在组内归一化成 z 分数，再加权求和。
  3. 留出 4 个属性不放进奖励，专门用来验收。
- **结果（step 100，CFG 2.0）：评委 R@1 从 7.8% 升到 13.0%，留出属性 +1.9 个点，孤儿率 −31%。**
  不加 CFG 时，留出属性 +5.1 个点。

## 5. 评估

- 192 条固定的验证集提示词，随机种子固定。指标包括：
  训练用的 CLIP（ViT-B/16）分数和检索 R@k；独立评委 CLIP（ViT-L/14）；CLIP 特征距离；
  属性分类器（在 CelebA 上微调的 ResNet-18，真实图上平均平衡准确率 0.952）；孤儿率；序列长度。
- CFG 会掩盖 RL 带来的变化，所以 cfg 1.0 和 2.0 分开评估。
- 生成的图存到磁盘，换评委或加新指标时只需要重新打分，不用重新生成。
- 图生图和临摹：与输入图的 PSNR。“分解器给前缀、模型续画”这种临摹方式：只给文字时 10.2 dB，
  给出前三层 18.7 dB，重画头发 19.8 dB，给出头发的粗轮廓再补细节 23.2 dB，纯分解器 29.7 dB。

## 6. 部署（`docs/runtime_design.md`）

- 导出成 5 个 ONNX 图，外加一个“cache 在图内更新”的版本（`chunk_cached`）。
  KV cache 改成由运行时管理的静态缓冲区；注意力手写（GQA 通过重复 KV 头实现），RMSNorm 也手写，以兼容 opset 18。
  ORT 与 PyTorch 的误差在 1e-5 以内。
- C++ 运行时：CMake 构建，链接 ORT 1.32。语法、采样、码本解码、光栅化都用 C++ 实现；
  KV cache 用 IOBinding 在显存里开两组缓冲交替读写（ping-pong）。
- 一致性：
  1. 逆 CDF 按词表顺序累计之后，Python ORT 与 PyTorch 6/6 条序列完全一致。
  2. C++ 与 Python ORT 4/6 条完全一致，剩下 2 条在第 100 条 record 之后才分叉，原因是画布光栅化的浮点差异。
  3. ORT 的 CUDA EP 默认打开 TF32，**会在 2–8 条 record 内就让采样分叉**；关掉之后 CPU 与 CUDA 6/6 一致。
- 速度：C++ CPU 版 288 records/s，Python 循环 40 records/s。在 batch 12、一次只算一个位置的情况下，
  GPU 上的瓶颈是 kernel 启动开销。下一步是 CUDA Graph、TensorRT 和 FP16/INT8 量化。
  量化之后不能再要求逐 token 一致，要用分布层面的指标来验收。

## 7. 面试可能会问的问题和回答要点

1. **为什么用自回归画笔触，而不是扩散模型？** 过程可读、可以编辑；能局部重画、续画；
   画面简单的地方用很少几笔就画完，计算量随内容复杂度变化。代价是要先造出“绘画过程”这种数据。
2. **数据从哪来，怎么保证质量？** 分解器的设计，PSNR 和量化误差的来源，清理规则，SHA 和协议哈希，防泄漏的划分方式。
3. **怎么判断瓶颈是数据、模型还是算力？** 训练和验证损失的差距；small 和 base 在同步数下的对比；
   1 → 4 条轨迹的消融实验。
4. **RL 怎么防止奖励作弊？** 用独立评委、留出属性、分项归一化，并把 CFG 的影响和 RL 本身的影响分开评估。
5. **多机怎么协同、怎么保证一致？** 按分片奇偶划分，原子写入加 SHA，用同一份源码跨 CUDA/HIP 编译，
   用 SHA 证明不同机器上重新生成的数据完全相同，链路慢时的工程取舍。
6. **DDP、FSDP、ZeRO 有什么区别，什么时候用哪个？** DDP 每卡一份完整模型，用 all-reduce 同步梯度；
   ZeRO-1/2/3 依次再切分优化器状态、梯度、参数；FSDP 相当于 ZeRO-3。小模型用 DDP 最简单；
   1B 在 24GB 的卡上需要 FSDP 加激活重计算。这个项目里 DDP 已经实现，并验证了正确性（第 2 节），扩展效率待测。
7. **为什么 GPU 上的推理比 CPU 还慢，怎么优化？** 自回归每次只算一个位置，batch 又小，kernel 启动开销占主导。
   用 IOBinding 把 cache 留在显存；用 CUDA Graph 消除启动开销；用 TensorRT 做算子融合；做批量和连续批处理。
8. **怎么验证导出和移植是正确的？** 先逐个图对比数值，再在同样的随机数下逐 token 对比序列；
   注意 TF32 这类隐藏的精度模式；记录第一次分叉的位置，并分析原因。
9. **讲一次性能优化的过程。** 先测出瓶颈，再改，再证明结果没变，最后测速度（`docs/perf_log.md` 里的 4 个例子）。
10. **在 DCU 上踩过什么坑？** 没有 Triton 和 torchvision，要写不依赖它们的实现；
    缺少 FlashAttention 的库，SDPA 要选 math 后端；wavefront 是 64；NumPy 1.x 读不了 NumPy 2 生成的 pickle。
