# 性能优化记录（2026-11-16）

每一项都写成同一个格式：怎么发现的 → 原因 → 改法 → 怎么证明没改坏 → 实测效果。
数字都是实测；不同机器、不同负载下测的会单独注明。

## 1. 训练吞吐：瓶颈在 CPU 数据加载，不在模型

**发现。** base（126M）的短测里，参数量是 small（20M）的 6 倍，速度却只慢 1.7 倍
（16175 vs 27243 records/s）。用两点做线性拟合：每条 record 的时间 ≈ 32 µs + 0.24 µs × 参数量（M）。
small 有 87% 的时间花在一个和模型大小无关的固定开销上。

**验证。** 第二阶段把 DataLoader worker 从 2 个改成 4 个，其他不变。稳定吞吐从约 26k 涨到
**44k records/s（1.7 倍）**。说明那部分固定开销主要是 worker 在 CPU 上组装样本：
build、perturb、按模式采样，都是 Python 逐条处理的。

**结论。** small 这种小模型，先看数据流水线跟不跟得上，再谈 kernel。
DCU 上 15 核的配额：4 个 torch 线程 + 4 到 6 个 worker 比较合适。

## 2. 画布检查点标记：一个 Python 循环花掉 37 ms

**发现。** 按阶段计时的工具 `bench/profile_train_step.py`（每个阶段前后都做同步，测各阶段单独的耗时）
显示，“构建训练画布”占了一步的 19%。读代码定位到 `checkpoint_flags`：它对 T ≈ 1000 个位置
逐个循环，每个位置发约 5 个很小的 GPU kernel，一个 batch 就是约 5000 次 kernel 启动。

**改法。** 原来的规则是串行的：数图元，遇到控制记录或数到第 k 个就标记，然后清零。
可以证明它等价于一个向量化的式子：两个控制记录之间，第 j 个图元是检查点，当且仅当 j 是 k 的倍数。
用 cumsum 算出累计图元数，用 cummax 取最近一次控制记录时的计数，两者相减得到 j，再判断 `j % k == 0`。
同一个函数里，逐个样本循环的 `searchsorted` 也改成了一次批量调用。

**证明没改坏。** 新增的测试把原来的循环版本留作参照，在随机生成的序列上逐位置比较，
序列里包括文本前缀、padding 和不同的 k。另外，原有的“训练画布 == 解码画布”逐像素测试也全部通过。

**效果。** 37 ms → 0.069 ms，**约 540 倍**（5070，B=32，T=1000）。

## 3. 冻结的文本编码器：每一步都在重复算同样的东西

**原因。** 中文描述是固定的集合（长、短描述及它们的镜像版本），
可是每一步都要把 32 条描述送进约 1 亿参数的 Chinese-CLIP 文本塔。

**改法。** 新增 `CachedTextEncoder`：以描述字符串为键做缓存，特征用 bf16 存在 CPU 上，
按 LRU 淘汰，避免随机模板描述让缓存无限增长。

**为什么数值不变。** 文本特征进模型后的第一步是 bf16 autocast 下的 `text_proj` 线性层，
输入本来就会被转成 bf16。所以缓存成 bf16，模型看到的数值完全一样。
训练中途画样图仍然用不带缓存的编码器，保证采样结果和以前一致。

**边界情况。** 淘汰要放在本 batch 取完数据之后，不然本 batch 要用的条目可能刚好被当成“最旧”淘汰掉。

## 4. 采样器：每一步的设备同步

**发现。** 用 cProfile 剖析真实权重下的采样：`Grammar.allowed_mask` 一项就占了 38%。
它为每个样本、每一步都在 GPU 上新建一个 mask，再用 Python 列表下标写入，每次都要来回同步。
此外，`int(event[b])`、`bool(live[b])` 之类逐样本读取 GPU 值的代码，也让 CPU 和 GPU 只能串行执行。

**改法。** 所有样本的语法 mask 先在 CPU 上构建好，一次拷到 GPU；
每生成一条 record，只用一次 `tolist()` 把 event 读回 CPU；
grammar、layer、live 都在 CPU 上用列表处理；
画布追踪器直接接收这些 CPU 列表，待画的图元按样本一次 `stack`，不再逐条写入。

**证明没改坏。** 用同一个种子，分别跑旧代码（git HEAD 打包出来的那一版）和新代码，
在无引导（RL rollout 用的设置）和 CFG=2 + top-p 两种模式下各生成 6 条序列。逐个 token 比较，**完全一致**。

**效果。** 27.5 → 13.8 ms/record（B=8，5070），**2 倍**。
剩下的时间主要是每步 9 次属性解码器调用产生的大量小 kernel。
下一步的方向是 CUDA Graph 或 C++ 运行时，这部分归到部署主线。

## 6. 传输链路

到 SCNet 的上传只有约 0.6–0.9 MB/s。实测排除了几种可能：
多路复用的单条 SSH 连接、每个文件单独开连接、暂停同时进行的下载，都没有明显改善。
下载约 6 MB/s。应对办法：

- 标签用 zstd 压缩能缩到 2%，序列分片缩到 56%。传输时一律用 `rsync -z`。
- 只要远程只拿来算 CLIP 特征或做预览，图片就打成 JPEG q95 包传（`tools/pack_jpeg.py`，
  和原图相比 42.7 dB，体积约为原始数组的 1/6）。分解目标和 PSNR 计算绝不用 JPEG。
- 只传后续步骤真正需要的数据。例如偶数分片在本地清理好再上传，评估只上传 600 张验证图。
- 如果以后租 GPU，要租能直接下载数据集的机器。
